CHAPTER 3
METHODOLOGY
This chapter describes the procedures and methods used to address the research problem and achieve the objectives of the study. It explains how the research was conducted, how data were collected and generated, how the BOPIS system was developed, and how the results will be analyzed and evaluated. The chapter is organized into nine sections: research design, sources of data, sampling data, system architecture, research instruments, data generation and gathering procedure, ethical considerations, data analysis, and statistical treatment.

Research Design
	This study employs a quantitative experimental research design aimed at evaluating the effectiveness of BOPIS in optimizing energy-efficient configurations for locally deployed Large Language Model (LLM) inference under controlled conditions.
The experiment is structured into three comparative conditions: unoptimized default configuration, random search, and BOPIS-optimized configuration. The unoptimized configuration represents standard deployment without tuning, while random search serves as deterministic and stochastic baselines, respectively. The BOPIS configuration is generated through Bayesian Optimization followed by Pareto-based multi-objective selection.
All experimental conditions are executed under identical hardware, software, model, and dataset settings to ensure fairness and internal validity. The same locally deployed LLM and the same standardized prompt dataset (Databricks Dolly 15k sample) are used across all conditions.
The dependent variables of the study include energy consumption, inference speed, output quality, and resource utilization. Any observed differences in results are attributed solely to the configuration selection strategy applied in each condition

Sources of Data
The study draws on a population frame or three categories of data sources: a standardized prompt dataset, hardware performance measurements, and configuration search outputs generated by the BOPIS system.
The primary prompt dataset used across all three experimental conditions is Databricks Dolly 15k, a publicly available instruction-following dataset containing approximately 15,000 human-generated prompts across eight task categories: open question answering, closed question answering, information extraction, summarization, classification, creative writing, brainstorming, and general-purpose instruction following. Dolly 15k was selected because it provides diverse prompt types representative of real-world LLM usage, includes reference outputs that enable proxy-based quality evaluation, and is freely accessible without licensing restrictions. The dataset is sourced from the official Hugging Face repository at https://huggingface.co/datasets/databricks/databricks-dolly-15k.
The second source of data is direct hardware measurement during LLM inference. Performance metrics, including energy consumption, inference speed, CPU and GPU utilization, and memory usage, are collected in real time during each experimental run using software-based monitoring tools described in the Research Instruments section. These measurements are generated by running the locally deployed LLM on the study's single-machine CPU-GPU setup under each of the three conditions.
The third source of data is the configuration evaluation log produced by the BOPIS Bayesian Optimization loop. Each evaluation of a candidate configuration during the BO search produces a record of the configuration parameters and their corresponding performance outcomes, which are used to update the Gaussian Process surrogate model and ultimately to construct the Pareto front from which the final recommended configuration is selected.

Sampling Data
	A stratified random sampling size approach is used to select a subset of prompts from the Databricks Dolly 15k dataset. From the full dataset of approximately 15,000 prompts, a sample of 500 prompts is extracted to ensure computational feasibility while maintaining representativeness.
Stratification is performed based on task categories to ensure proportional representation of each category in the final sample. Within each category, prompts are randomly selected without replacement. Additional filtering is applied to remove prompts that exceed the maximum token length supported by any tested configuration, as well as prompts with missing reference outputs.
The resulting 500-prompt dataset is fixed prior to experimentation and is used consistently across all three conditions: unoptimized, random search, and BOPIS. This ensures that performance differences are attributable to configuration strategies rather than dataset variation.
A smaller subset of 50 prompts is used during intermediate evaluations within the optimization process to reduce computational cost while preserving representativeness.

System Architecture

Figure 3.1 System Architecture
	The BOPIS system is composed of five major components: the Input Layer, the BOPIS Optimization Engine, the Performance Measurement Layer, the Benchmark Comparison Conditions, and the Output and Statistical Analysis Layer. These components operate as an integrated experimental pipeline that transforms inference configuration parameters into statistically validated energy-efficient LLM deployment recommendations.
The Input Layer provides the resources and parameters required for inference optimization and evaluation. It includes the hardware environment specifications, the llama.cpp inference engine, the configuration search space parameters, and the Databricks Dolly 15K dataset used for benchmark prompts and reference outputs. These inputs are shared consistently across all experimental conditions to ensure fair comparison.
Inside the BOPIS Optimization Engine, the Configuration Space Definition module establishes the discrete search space explored during optimization. The configuration parameters include input token length (128, 256, 512, 1024), batch size (1, 2, 4, 8), numerical precision (FP32, FP16, INT8), GPU layer offloading (0, 14, 28, all), and CPU thread allocation (2, 4, 8). These parameters are evaluated consistently across the unoptimized baseline, random search, and BOPIS optimization conditions.
The Bayesian Optimization Engine serves as the primary intelligent search mechanism of BOPIS. The engine uses a Gaussian Process (GP) surrogate model to approximate the relationship between inference configurations and observed performance outcomes. The Expected Improvement acquisition function selects candidate configurations by balancing exploration of uncertain regions and exploitation of configurations predicted to yield favorable results. The surrogate model is iteratively updated after each inference evaluation using newly collected measurements from the Evaluation Module.
The Evaluation Module executes LLM inference using llama.cpp subprocess calls under the candidate configuration provided by the optimization engine. Each evaluated configuration produces inference outputs and execution logs which are forwarded to the Performance Measurement Layer for monitoring and analysis.
The Performance Measurement Layer operates passively across the entire optimization and benchmarking pipeline. This layer records energy consumption, inference speed, output quality, and resource utilization metrics for every evaluated configuration. GPU power draw, utilization, and VRAM consumption are collected directly through the NVIDIA Management Library (NVML) accessed via Python ctypes. CPU utilization, RAM usage, and thread activity are retrieved from the Linux /proc filesystem. Inference speed in tokens per second is extracted from llama.cpp execution logs, while output quality is evaluated using BERTScore F1 against Databricks Dolly 15K reference outputs. All measurements are logged into structured CSV datasets using researcher-developed scripts without reliance on third-party monitoring frameworks.
The Pareto Analysis Module performs multi-objective evaluation on all measured configurations. The module identifies Pareto-optimal solutions across the competing objectives of minimizing energy consumption, maximizing inference speed, and maximizing output quality. From the resulting Pareto front, BOPIS selects the final recommended configuration based on energy-efficiency priority while maintaining acceptable performance thresholds.
To validate optimization effectiveness, the architecture includes two comparison conditions: the unoptimized default configuration and a random search baseline. These conditions bypass the Bayesian Optimization Engine but still execute through the same evaluation and measurement pipeline to ensure experimental consistency. All three conditions generate benchmark results and structured statistical analysis datasets.
The Output Layer consolidates the experimental outputs of the system. These outputs include benchmark comparison results, statistical analysis datasets, Pareto front solutions, and the final optimal configuration identified by BOPIS. The statistical analysis pipeline applies descriptive statistics, the Friedman test, and post-hoc Nemenyi analysis to determine whether statistically significant differences exist among the unoptimized baseline, random search baseline, and BOPIS optimization model.

Figure 3.2 BOPIS Optimization Model
Figure 3.2 presents the theoretical optimization model of BOPIS. The model formalizes how Bayesian Optimization and Pareto-based selection are used to identify energy-efficient inference configurations for locally deployed Large Language Models (LLMs). Unlike the system architecture, which focuses on component interaction and data flow, the BOPIS Optimization Model describes the computational decision-making process used to evaluate, optimize, and select inference configurations.
The optimization process begins with the definition of the inference configuration vector:
x = (t, b, p, g, c)
Where:
(t)= input token length
(b) = batch size
(p)= numerical precision
(g) = GPU layer offloading configuration
(c) = CPU thread allocation
Each configuration vector represents one candidate inference setup evaluated by the model.
The study treats LLM inference optimization as a constrained multi-objective optimization problem. The objective function of BOPIS is defined as:
f(x) = {E(x), -S(x), -Q(x)}
where:
E(x) = energy consumption
S(x)  = inference speed
Q(x)  = output quality
Since optimization procedures are conventionally formulated as minimization problems, inference speed and output quality are represented as negative terms to indicate maximization objectives.
The primary optimization goal of BOPIS is to minimize energy consumption while maintaining acceptable inference speed and output quality thresholds. This is formally represented as:
x*=argmin E(x)
subject to:
S(x)  Smin(H) 
Q(x)Qmin(task) 
where:
(x) represents the configuration search space
(Smin) represents the minimum acceptable inference speed
(Qmin) represents the minimum acceptable output quality threshold
Bayesian Optimization is used as the primary search mechanism of the model. A Gaussian Process (GP) surrogate model approximates the relationship between inference configurations and observed performance outcomes. The surrogate model is iteratively updated after each evaluation using newly observed measurements collected from LLM inference execution.
The Expected Improvement (EI) acquisition function is used to determine the next configuration to evaluate. The acquisition function balances exploration of uncertain regions in the search space and exploitation of configurations predicted to produce favorable results.
After candidate configurations are evaluated, Pareto analysis is applied to identify non-dominated solutions across the competing objectives of energy consumption, inference speed, and output quality. A configuration is considered Pareto-optimal if no other configuration improves one objective without degrading at least one other objective. This condition is formally defined as: fi(x)fi(x*) i  and fj(x)  fj(x*) for at least one j
The resulting Pareto front represents the set of optimal trade-off configurations identified by BOPIS. From this set, the final recommended configuration is selected based on energy-efficiency priority while preserving acceptable performance thresholds.

Research Instrument
	In strict adherence to the institutional guidelines, the primary research instruments used in this study are the structured experiment papers designed to systematically document performance measurements during the execution of local Large Language Model (LLM) inference. These instruments are applied consistently across all three experimental conditions such as unoptimized default configuration, random search baseline, and BOPIS-recommended configuration to ensure fair, reproducible, and statistically valid comparison.
The experiment papers record all dependent variables per trial: total energy consumption in Joules (J), normalized energy per generated token (J/token), inference throughput in tokens per second (tokens/sec), output quality as BERTScore F1, and hardware resource utilization including CPU utilization, GPU utilization, and memory usage. Recorded values are cross-verified against raw log files before statistical analysis to detect and correct any transcription or instrumentation discrepancies.
Inference Engine
	The LLM is executed using llama.cpp, an open-source C++ inference engine for running quantized large language models on commodity hardware. llama.cpp is invoked through Python’s built-in subprocess module as an external process, meaning it is called the same way any command-line program is called,  no Python binding or wrapper package is imported. llama.cpp produces structured execution logs containing wall-clock inference duration and token counts (n_prompt_tokens and n_generated_tokens) per inference call. These log values are parsed by the researchers’ own Python scripts using only the standard library’s string and file I/O methods.
GPU Power Measurement
GPU power draw is captured by interfacing directly with the NVIDIA Management Library (NVML) through Python’s built-in ctypes foreign function interface. ctypes is part of the Python standard library and requires no installation. It loads libnvidia-ml.so, the same shared driver library that nvidia-smi itself calls, and invokes nvmlDeviceGetPowerUsage() directly on the GPU device handle. This bypasses any third-party Python wrapper and reads power consumption in milliwatts straight from the NVIDIA driver layer. Readings are collected at fixed 100-millisecond intervals throughout each inference call and stored in memory for post-run energy computation.
CPU and Memory Utilization
CPU utilization percentage, RAM usage, and thread activity are read from the Linux /proc filesystem, a virtual filesystem exposed by the operating system kernel that provides real-time hardware and process state without requiring any external package. Specifically, /proc/stat is parsed for CPU time counters, /proc/meminfo for memory availability, and /proc/[pid]/status for per-process thread count and memory footprint. All parsing is performed using Python’s standard file I/O and string-splitting operations.
GPU Utilization and VRAM
GPU utilization percentage and VRAM usage are queried using the same direct NVML interface described above, calling nvmlDeviceGetUtilizationRates() and nvmlDeviceGetMemoryInfo() respectively. These calls are made at the same 100-millisecond sampling interval as power readings, ensuring temporal alignment across all GPU metrics.
Hardware Profiling
	Prior to experimentation, the research machine is profiled to identify its hardware specifications. CPU model, core count, and thread count are read from /proc/cpuinfo. GPU model, total VRAM, CUDA capability, and supported numerical precision formats are queried via NVML through ctypes. Total installed RAM is read from /proc/meminfo. These measurements constrain the valid configuration space used by BOPIS and justify hardware-aware configuration recommendations.
Output Quality Measurement
	Output quality is evaluated using BERTScore F1. The BERTScore computation is implemented by the researchers using Python standard library math operations, computing token-level cosine similarity between contextual embedding vectors obtained from a locally loaded BERT model checkpoint. Generated responses are compared against reference outputs from the Databricks Dolly 15k dataset. BERTScore F1 is selected over exact-match metrics because it captures semantic similarity, making it appropriate for instruction-following tasks where multiple valid phrasings exist for the same correct answer.

Data Generation/Gathering Procedure
Data collection proceeds through five stages executed in the following order. All monitoring, logging, and metric extraction across every stage is performed exclusively through direct OS and driver interfaces — the Linux /proc filesystem and the NVIDIA NVML library via ctypes; and Python standard library operations. No third-party monitoring package is used at any stage.
Stage 1: Environment Setup and Instrument Verification
	The single-machine CPU-GPU hardware environment is configured and validated. llama.cpp is installed with all required quantized model weights and verified to run correctly. The researchers’ Python scripts that interface with NVML via ctypes and parse /proc filesystem entries are tested against a warm-up inference run of ten consecutive calls whose results are discarded. This warm-up ensures GPU clock states and memory allocation are stable before data collection begins.
	A baseline idle power measurement is then recorded. With no inference process running, the NVML ctypes interface samples GPU power draw every 100 milliseconds for 60 consecutive seconds. The mean of these samples is stored as P_idle and is used throughout all subsequent stages to isolate inference-induced energy from background system power consumption.
	The 500-prompt stratified sample from Databricks Dolly 15k is prepared and saved to disk along with the corresponding reference outputs. The 50-prompt Bayesian Optimization evaluation subset is drawn from this sample and saved separately.
Stage 2: Unoptimized Baseline Measurement
	The LLM is run under its default configuration across all 500 sampled prompts. Each prompt is submitted individually as a subprocess call to llama.cpp. Throughout each inference call, the NVML ctypes interface samples GPU power draw at 100-millisecond intervals and stores the readings in a timestamped list. Upon completion of the call, llama.cpp’s execution log is parsed to extract wall-clock inference duration (Δt) and generated token count (N_gen). CPU utilization, RAM usage, GPU utilization, and VRAM usage are read from /proc filesystem entries and NVML at the end of each call. All raw values are written to a structured CSV log file by the researchers’ Python scripts. This process repeats for all 500 prompts. BERTScore F1 for each response is computed after all inference calls are complete by comparing generated outputs against Dolly 15k reference outputs.
Stage 3: BOPIS Optimization Run
	The Bayesian Optimization Engine is initialized with the Configuration Space Definition and five randomly selected initial configurations to seed the Gaussian Process surrogate model. The GP surrogate and the Expected Improvement acquisition function are implemented entirely in Python using only standard library math operations — no optimization or machine learning library is used. For each BO iteration, the Engine selects the next configuration, llama.cpp is invoked on the 50-prompt evaluation subset under that configuration, performance metrics are collected through the same NVML ctypes and /proc-based monitoring pipeline used in Stage 2, and the GP surrogate is updated with the new observation. This process repeats for a fixed number of iterations.
	Upon completion, the Pareto Analysis Module evaluates all observed configurations. Non-dominated sorting is performed using the researchers’ own Python implementation of Pareto dominance checking, selecting configurations where no other observed configuration is simultaneously better on all objectives. The recommended configuration is selected from the Pareto front and validated by running the full 500-prompt dataset under the same measurement pipeline as Stage 2.
Stage 4: Random Search Baseline
	A Random Search baseline is executed for fair comparison against BOPIS. Configurations are sampled uniformly at random from the same configuration space, with the number of samples matched to the total number of BO iterations to ensure equal evaluation budget. Each configuration is evaluated on the same 50-prompt subset using the same NVML ctypes and /proc-based monitoring pipeline. After all configurations are evaluated, the best-performing one is selected and validated using the full 500-prompt dataset under the same measurement pipeline as Stages 2 and 3.
Stage 5: Data Consolidation
	All CSV log files from Stages 2, 3, and 4 are consolidated into a single structured dataset using the researchers’ own Python scripts. For each of the three conditions, final performance records contain all raw per-prompt values alongside computed mean and standard deviation across the 500-prompt evaluation runs. Raw log values are cross-verified against experiment paper entries before this dataset is passed to statistical analysis.

Data Analysis (Procedure and Treatment)
Data analysis proceeds in two phases: descriptive analysis and inferential statistical analysis.
In the descriptive phase, performance data for all dependent variables are summarized per condition using mean, standard deviation, minimum, and maximum values computed across the 500-prompt evaluation runs. Energy consumption is reported both as total Joules and as normalized Joules per token (J/token). Inference speed is reported as mean tokens per second (tokens/sec). Output quality is reported using mean BERTScore F1. Resource utilization is reported through mean CPU utilization, GPU utilization, and memory usage. These descriptive statistics provide an overall performance profile for each configuration condition.
In the inferential phase, the Friedman test is applied separately to each dependent variable to determine whether statistically significant differences exist among the three evaluated configurations: unoptimized default configuration, random search baseline, and BOPIS-optimized configuration. Since the same prompt dataset is evaluated under all three conditions, the Friedman test is appropriate for comparing related samples without assuming normality.
The null hypothesis states that there is no statistically significant difference among the three configurations for a given dependent variable. The alternative hypothesis states that at least one configuration differs significantly from the others. A significance level of α = 0.05 is used for all statistical tests. If the computed p-value is less than 0.05, the null hypothesis is rejected.
All statistical analysis is conducted using the researchers' own Python implementations of the Friedman test and Nemenyi post-hoc comparison, built from standard library math and statistics operations. Visualizations including grouped bar charts, energy-performance trade-off plots, and Pareto front visualizations are generated using standard library file output formatted for plotting, with no third-party visualization package.

Statistical Treatment
The statistical treatment applied in the study is intended to determine whether there are statistically significant differences among the unoptimized default configuration, the random search baseline, and the BOPIS-optimized configuration across all dependent variables.
The Friedman test will be used as the primary statistical test in the study. The test will be applied separately to each dependent variable: energy consumption measured in Joules and Joules per token (J/token), inference speed measured in tokens per second (tokens/sec), output quality measured through BERTScore F1, and resource utilization measured as CPU utilization (%), GPU utilization (%), and memory usage (MB).
Since the same prompt dataset is evaluated under all three configurations, the Friedman test is appropriate for comparing related samples without assuming normality of the data. The null hypothesis states that there is no statistically significant difference among the three configurations for each dependent variable. The alternative hypothesis states that at least one configuration differs significantly from the others.
A significance level of α = 0.05 will be used for all statistical tests. If the computed p-value is less than 0.05, the null hypothesis will be rejected.
In addition, if significant differences are found, post-hoc pairwise comparisons using a suitable non-parametric method (e.g., Nemenyi test) will be conducted to identify which specific configurations differ.
Descriptive statistics, including mean, standard deviation, minimum value, and maximum value will also be computed for all dependent variables to summarize the performance of each configuration.
BERTScore F1 will be used as the primary output quality metric because it evaluates semantic similarity between generated responses and reference outputs using contextual embeddings, making it suitable for evaluating Large Language Model-generated text.
